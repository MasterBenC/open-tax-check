# 税务健康检查基础框架设计

**日期：** 2026-07-28  
**状态：** 已确认，待实施  
**实施范围：** 第一批——基础框架  
**长期覆盖期间：** 2023–2026 年

## 背景

OpenTaxCheck 已具备安全读取客户账套、标准化会计数据和执行确定性检查的基础。下一阶段要把它扩展为客户宿主 Agent 可调用的税务健康检查工具：

1. 客户提交账套和其他资料；
2. 核心程序立即形成首版《税务健康检查报告》；
3. 资料缺失或事实冲突时，客户宿主 Agent（例如 WorkBuddy）向客户集中提问；
4. 客户回答或补交资料后，仅重新运行受影响的税种；
5. 报告持续更新，未解决事项始终显式保留。

运行环境中通常没有税务专业人员，因此系统不设置专业人员审批门槛。它定位为客户内部自用的自动化检查工具，不出具涉税鉴证、专业税务意见或申报结论。

## 目标

- 定义稳定的税种注册、规则版本、事实、问题、确认和报告接口。
- 在不绑定任何模型供应商的前提下，让宿主 Agent 能够补齐资料。
- 客户上传资料后立即生成渐进式报告，不等待全部问题解决。
- 对资料不足、地方政策缺失和事实冲突保持失败闭合，不猜测结论。
- 记录规则版本、官方来源、客户确认和证据引用，保证结果可追溯。
- 控制模型成本：确定性程序优先，AI 只处理真正需要交互的缺口。
- 为后续 2023–2026 年全税种筛查包和计算规则包提供兼容基础。

## 非目标

第一批基础框架不：

- 声称已完成全部税种的实质计算规则；
- 自动抓取或在运行时联网更新税法；
- 在 Python 核心中直接调用 LLM API；
- 代替客户完成申报、缴税或账务调整；
- 出具涉税鉴证、税务审计、专业税务意见或无保留合规结论；
- 要求不存在于客户环境中的税务专业人员签字或审批；
- 建设用户账户、聊天界面、模型路由或托管式 Agent 平台；
- 猜测缺失的地方税率、减免资格或关键交易事实。

## 长期税种范围

注册表最终覆盖中国现行 18 个税种：

1. 增值税；
2. 消费税；
3. 企业所得税；
4. 个人所得税；
5. 资源税；
6. 城市维护建设税；
7. 房产税；
8. 印花税；
9. 城镇土地使用税；
10. 土地增值税；
11. 车辆购置税；
12. 车船税；
13. 船舶吨税；
14. 耕地占用税；
15. 契税；
16. 烟叶税；
17. 环境保护税；
18. 关税。

另注册教育费附加和地方教育附加，共 20 个检查项目。全部项目都必须具备适用性筛查、资料缺口和官方来源；只有事实、证据和规则参数充分时才允许计算。

## 方案选择

采用项目自有的轻量级清单式规则注册表，不直接引入 OpenFisca 等微观模拟框架。

自有注册表更符合当前 Apache-2.0 项目、离线执行、审计溯源和低依赖要求。OpenFisca、PolicyEngine 和 Tax-Calculator 可用于参考期间参数与测试组织方式，但其许可证、国家范围或家庭微观模拟模型与本项目不完全匹配。GitHub 上的中国税务助手类项目可帮助发现税种和业务场景，不作为权威规则来源。

## 总体架构

### `tax_profile`

保存从客户资料推断出的事实草稿，例如主体类型、纳税人身份、经营地区、交易类型和检查期间。

事实分为三类：

- `observed`：可直接从证据读取；
- `inferred`：程序或宿主 Agent 推断，尚未确认；
- `confirmed`：客户已明确确认，或有充分权威证据支持。

关键事实不得仅凭 AI 推断进入确定性结论。纳税人身份、适用税率、交易性质、资产所在地、优惠资格等必须有证据或客户确认。

### `tax_registry`

注册 20 个稳定税种标识、中文名称、类别和规则包入口。注册表不包含易变税率；易变内容全部进入版本化规则包。

### `tax_packs`

每个规则包至少声明：

- 税种标识和适用地区；
- `effective_from` 与 `effective_to`；
- 适用性条件；
- 所需事实和证据类型；
- 可选计算或一致性检查入口；
- 地方参数要求；
- 官方来源名称、链接和发布日期；
- 规则包版本。
- 成熟度：`prototype`、`screening` 或 `calculation`。

全国基线规则与省级扩展分离。缺少适用的地方扩展或参数时返回 `needs_local_policy`。
注册项尚无覆盖当前期间的正式规则包时仍必须出现在报告中，并返回
`blocked` 和稳定诊断 `rule_pack_unavailable`，不得省略该税种或调用 AI 猜测规则。

### `tax_screening`

协调资料事实、规则选择和各税种执行，输出逐税种状态、发现事项、证据缺口和受影响事实键。它不负责和用户对话，也不负责渲染最终文档。

### `question_queue`

将多个税种共同依赖的事实合并成一次客户问题。每个问题包含：

- 稳定问题 ID；
- 受影响税种；
- 待确认事实键；
- 提问原因；
- 可接受的答案结构；
- 可提交的证据类型；
- 优先级；
- 是否为阻断性问题。

问题中不得包含模型隐藏推理，也不得要求宿主 Agent复述客户账套中的非必要敏感内容。

### `confirmations`

宿主 Agent 将客户答案或补充资料转换为结构化确认记录：

- 问题 ID；
- 事实键和结构化答案；
- 证据引用；
- 确认主体；
- 确认时间；
- 来源类型。

核心程序必须校验答案结构和证据引用。无效确认不得静默覆盖原事实。

### `report_assembler`

根据检查快照生成《税务健康检查报告》。报告生成与规则执行分离，使 Markdown、JSON 或未来的其他输出格式共享同一组确定性结果。

### `audit_trail`

记录输入文件哈希、规则包版本、规则来源、问题、客户确认、状态变化和重跑原因。不记录模型隐藏推理，不复制无关客户原始数据。

## 数据流

1. 客户资料经过现有安全入口完成清点和解析。
2. 系统建立 `tax_profile` 事实草稿。
3. 注册表为检查期间和地区选择相应规则包。
4. 20 个检查项目分别产生状态、发现事项和资料缺口。
5. 报告组装器立即生成首版《税务健康检查报告》。
6. 共同缺口被去重并写入 `question_queue`。
7. 宿主 Agent 将相关问题合并后向客户提问。
8. 客户答案或补充文件形成 `confirmations`。
9. 依赖图定位受影响税种，仅重跑这些税种。
10. 生成新报告版本，并在审计记录中保留变化。

首版和后续版本都是有效的渐进式报告。系统不设置“必须回答完所有问题才能出报告”的全局门槛。

## 逐税种状态

每个检查项目必须且只能处于以下状态之一：

- `calculated`：事实、证据和规则充分，已完成适用计算或检查；
- `not_applicable`：有充分证据确认不适用；
- `needs_evidence`：缺少客户资料或关键事实确认；
- `needs_local_policy`：缺少适用地区的税率、减免或其他地方参数；
- `blocked`：资料冲突、格式错误或其他原因使系统无法可靠判断。

只有 `calculated` 和 `not_applicable` 可以形成明确的逐税种结论。其余状态必须进入问题队列或报告限制说明，不得被汇总成“无风险”或“合规”。

## 报告边界

正式名称统一为《税务健康检查报告》。

封面和固定免责声明必须明确：

- 本报告仅供客户内部自查；
- 本报告不属于涉税鉴证、专业税务意见或纳税申报结论；
- 结果取决于客户提供的资料、确认事实和所选规则版本；
- 资料不足或政策缺失的项目未形成确定结论；
- 客户自行决定是否申报、调整或另行咨询专业机构。

免责声明不是替代技术控制的免责捷径。系统仍必须执行事实确认、证据完整性检查、规则溯源、失败闭合和未决事项披露。

报告不得：

- 使用“已全面合规”“不存在税务风险”等全局断言；
- 把 `needs_evidence`、`needs_local_policy` 或 `blocked` 显示为通过；
- 展示宿主模型的隐藏推理；
- 冒充税务师、会计师事务所或税务机关出具的文书；
- 预留专业人员签字、盖章或二级复核栏。

## AI 参与边界与成本控制

Python 核心不直接依赖任何模型，也不负责自由文本对话。宿主 Agent 只通过 `question_queue` 和 `confirmations` 两个结构化契约参与。

成本控制规则：

- 文件解析、规则选择、计算、重跑和报告生成不调用模型；
- 只有缺失事实、资料冲突或无法可靠分类时才产生 AI 交互任务；
- 同一事实影响多个税种时合并提问；
- 客户已经确认的事实按证据哈希和作用域缓存；
- 新确认只触发受影响税种的增量重跑；
- 普通提取和分类允许宿主使用小模型，复杂冲突再由宿主自行升级；
- 宿主可以设置项目级调用次数、轮次或 Token 上限；
- 达到上限后仍生成报告，未解决事项保持原状态。

核心接口不传递模型供应商、模型名称或 Token 计费字段，以免把宿主策略固化进税务核心。

## 规则来源与版本管理

2023–2026 年规则以全国人大、国务院、财政部、国家税务总局、海关总署及适用省级机关发布的官方文件为最终依据。

运行时离线选择规则，不实时抓取网页。规则维护阶段可以联网核验，但写入规则包时必须保存官方来源链接、发布日期、生效期间和人工可读摘要。第三方文章和 GitHub 仓库只能作为检索线索。

规则验证至少检查：

- 同一税种和地区的生效期间是否异常重叠；
- 声称已覆盖 2023–2026 的正式规则包是否存在未声明空档；
- 是否缺少官方来源；
- 结束日期是否早于开始日期；
- 全国基线与地方扩展是否错误覆盖；
- 参数类型、单位和允许范围是否有效。

## 错误处理

- 输入文件损坏继续使用现有稳定诊断，不进入 AI 猜测流程。
- 同一事实出现冲突时保留全部证据引用，并将相关税种设为 `blocked`。
- 客户回答无法通过结构校验时保留原状态，并产生可理解的修正问题。
- 未找到期间规则时返回稳定的规则缺失诊断，不使用最接近年份代替。
- 宿主 Agent 不可用时，核心仍能生成含缺口的报告和机器可读问题清单。
- 任一税种失败不得清除其他税种已获得的结果。

错误和日志不得泄露客户文件的原始单元格内容、完整本地路径或无关个人信息。

## 交付拆分

### 第一批：基础框架

本设计对应的实施计划只覆盖：

- 税种注册表和版本化规则包模式；
- 事实、状态、问题、确认和审计数据结构；
- 期间与地区规则选择；
- 问题去重；
- 增量重跑依赖接口；
- 《税务健康检查报告》的机器可读快照和基础文本渲染；
- 少量无实质税率声明的示例规则包，用于验证框架。

示例规则包必须标记为 `prototype`。第一批不得宣称已完成 20 个项目的实质筛查或计算；尚未具备正式规则包的注册项统一按 `rule_pack_unavailable` 处理。

### 第二批：全税种筛查

20 个项目全部补齐 2023–2026 全国基线的适用性判断、资料清单和官方来源；地方规则缺失时保留 `needs_local_policy`。

### 第三批：计算与一致性规则

先实现增值税、企业所得税、个人所得税、附加、印花税和契税，再补齐其他税种。每次只在输入和参数足够时计算。

第二批和第三批分别进行设计、书面确认和实施计划，不在第一批中提前扩张。

## 测试策略

第一批严格采用测试驱动开发。至少覆盖：

1. 20 个稳定注册项无缺失、无重复；
2. 规则包模式拒绝缺少期间、来源或无效参数的清单；
3. 期间边界在生效日和失效日选择正确版本；
4. 地方扩展优先于全国基线，缺失时状态正确；
5. 五种状态互斥且序列化稳定；
6. 多税种共同事实只生成一个问题；
7. 客户确认只重跑受影响税种；
8. 无效确认不能覆盖现有事实；
9. 宿主 Agent 缺席时仍能生成报告；
10. 报告不会把未决状态描述为通过；
11. 报告固定包含免责声明和规则版本；
12. 审计记录不含模型隐藏推理或不必要客户原文；
13. 现有账套、安全入口、标准化和会计规则测试全部回归通过。

后续实质规则必须额外覆盖年度切换、边界值、资料不足、地方参数缺失和经脱敏处理的历史案例。

## 验收标准

- 新测试先在缺少实现时按预期失败，再通过最小实现转绿；
- 第一批公开接口具备类型、示例和稳定序列化测试；
- 基础报告可在没有宿主 Agent 和未回答问题的情况下生成；
- 所有未决项目在报告和机器可读输出中保持一致；
- 完整源代码测试套件无失败，平台条件跳过如实报告；
- 构建、严格发行验证和 `git diff --check` 通过；
- 独立代码复核无 Critical 或 Important 问题；
- 不新增直接 LLM 依赖；
- 不改变现有“借贷必须平衡”的会计不变量。
