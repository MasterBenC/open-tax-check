# OpenTaxCheck 客户报告重设计

**日期：** 2026-08-02

**状态：** 已确认设计，待实施

**范围：** 《税务健康检查报告》的内容架构、客户结论准入、DOCX/PDF 版式和交付验收

## 1. 问题与目标

当前报告能够列出税种结果、计算过程、问题和规则来源，但整体仍像机器结果清单：管理层无法快速判断需要关注什么、为什么关注、下一步做什么；技术字段、重复问题和长篇规则来源挤占正文；DOCX 结构过于简单；宿主 AI 智能体可能另外撰写一份与案件快照不受控的摘要。

新报告采用“老板版主报告 + 专业附录”。前 5–8 页提供清楚、克制、可行动的管理层信息；附录保留税务计算、证据、规则和审计血缘。两者必须来自同一案件快照，AI 智能体不得自行升级结论或另写不受控摘要。

## 2. 核心原则

- 报告首先帮助企业负责人理解当前状态和下一步，不要求其理解内部状态码或公式 ID。
- 排版和图表不得掩盖资料不足、未执行程序或未确认事实。
- 不提供总体健康分，不用资料完整度伪造精确百分比。
- “试算金额”不等于应补税额、欠税金额或最终申报金额。
- 未复核语义候选不进入客户风险结论。
- “本次范围内未见异常”只描述已执行程序，不等于无风险。
- 报告生成不要求税务专业人员签字、盖章或批准，但必须包含边界和免责声明。
- Markdown、DOCX、PDF、工作底稿、机器快照和证据包必须绑定同一案件修订。

## 3. 报告组成

### 3.1 老板版主报告

老板版控制在 5–8 页，包含：

1. **封面**：企业名称、检查期间、报告状态、修订号和生成日期；
2. **管理层摘要**：一句话状态、重点核实数量、待补资料数量、待核对试算数量；
3. **老板先看这些事**：按优先级列出重点核实事项；
4. **资料缺口及影响**：缺什么、影响哪些税种或判断、如何补充；
5. **建议行动顺序**：立即核对、近期补齐、后续完善三层行动；
6. **检查范围和限制**：已收资料、未收资料、已执行程序、未执行程序；
7. **免责声明**：内部健康自查，不属于鉴证、税务意见、申报结论或税务机关认定。

管理层摘要不展示内部英文状态码、公式 ID、完整法规标题列表或原始 JSON 字段。试算金额只有在确有管理意义时显示，并紧邻固定免责声明。

### 3.2 专业附录

专业附录页数不设硬上限，至少包含：

- 各税费项目状态和适用性依据；
- 已确认计税事实与证据等级；
- 试算公式、税基、税率、扣除和结果；
- 账务勾稽与申报勾稽；
- 资料覆盖矩阵和未执行程序；
- 客户确认问题及审计事件；
- 规则包、规则版本、官方来源和适用期间；
- 输入资料哈希、报告修订和交付文件哈希。

法规正文不堆入老板版。附录显示简短依据、文号、适用条款和来源链接；完整官方材料仍由规则包和证据包保存。

## 4. 客户结论分级

客户报告只使用以下四类中文状态：

| 状态 | 使用条件 | 禁止升级 |
| --- | --- | --- |
| 重点核实 | 存在确定性差异、矛盾或经准入的复核事项 | 没有充分证据时不得写成漏缴、违规或确定风险 |
| 待补资料 | 缺申报表、合同、完税凭证、当地政策或客户确认 | 不得改写为不适用或无风险 |
| 账务勾稽提示 | 账簿之间或账簿与试算口径存在差异 | 不得把结果反推为正式计税依据 |
| 本次范围内未见异常 | 已执行的确定性程序未发现异常，且范围明确 | 不得简称“无风险”或扩展到未执行程序 |

`candidate` 或 `unreviewed` finding 不进入上述结论。确有必要向客户了解业务背景时，转换为中性的“资料核对事项”，只说明需要什么资料和为什么需要，不给出税务定性。

## 5. 单项重点事项模板

每项重点事项固定包含：

1. **发现了什么**：直接说明确定性观察或差异；
2. **为什么需要关注**：说明可能影响的税种、申报或账务环节；
3. **目前不能下什么结论**：明确证据和程序边界；
4. **需要补什么资料**：列出可验证的材料或客户回答；
5. **建议下一步**：给出可执行核对动作。

模板字段来自机器合同。AI 可以在不改变事实、金额性质和强度的前提下做轻微中文润色，但最终交付内容由核心渲染器生成。

## 6. 报告状态与固定措辞

- 存在待补资料或待确认事项：标题使用“第一轮账务初筛已完成”或“初版报告已生成”；
- 案件状态为 `completed_with_limitations`：仍称初版或受限完成，不称完整检查完成；
- 只有 Python 案件状态为 `completed` 时，才能使用“本次可执行检查程序已完成”；
- 试算汇总紧邻固定文字：“试算金额不代表应补税额、欠税金额或最终申报金额。”；
- 没有申报表、完税凭证或其他反向证据时，不使用“漏缴”“少缴”“违规”；
- 有待补资料时，limitations 不得为空；系统自动从待补事实、当地政策缺口和未执行程序生成可见限制。

## 7. 输出和数据绑定

同一案件修订生成：

- `税务健康检查报告.md`：内容基准；
- `税务健康检查报告.docx`：主要客户交付；
- `税务健康检查报告.pdf`：有可靠渲染器时生成；
- `workpaper.xlsx`：内部复核底稿；
- `tax-health-snapshot.json`：脱敏机器快照；
- 证据包和交付清单；
- 结构化客户交付说明。

以上文件绑定相同的案件修订号、输入资料哈希、确认事实版本、规则包版本和生成时间。交付清单仅列出实际存在且 SHA-256 匹配的文件。AI 智能体不得另外制作与该修订无绑定关系的“最终摘要”。

## 8. DOCX 与 PDF 版式

DOCX 至少包含：

- 独立封面；
- 自动或静态目录；
- 老板版与专业附录分隔页；
- 多级中文标题；
- 重点事项、资料缺口和行动计划表格；
- 页眉、页脚、页码、企业名称和修订号；
- 适合中文阅读的字体回退和段落间距；
- 可重复的表头和合理分页；
- 附录内部链接或可读目录层级。

视觉风格采用克制的专业商务风。颜色只用于区分重点核实、待补资料、账务提示和范围内未见异常；不使用红色制造已经定性的风险印象，不使用环形评分或总体健康分。

PDF 只在可靠渲染器可用时生成。渲染器不可用返回明确的 partial 状态，不伪造 PDF，也不把 DOCX 结构检查称为视觉验收通过。

## 9. 验收

### 9.1 内容验收

- 一份序时账和十二项资料缺口的案例不得称检查完成；
- 没有确认审计事件时不得声称存在客户确认事实；
- 反推所得税、房产税或土地使用税税基不得进入正式计算依据；
- 未复核“茶叶”等语义候选不得进入客户重点结论；
- 试算汇总必须紧邻金额性质声明；
- limitations 必须包含待补资料和未执行程序；
- 老板版不出现内部英文状态码、公式 ID 或原始 JSON 字段。

### 9.2 结构验收

- Markdown 包含规定章节且顺序稳定；
- DOCX 包含封面、目录、分隔页、标题层级、表格、页眉页脚和页码；
- 老板版内容在专业附录之前；
- 交付文件来自同一快照修订且哈希匹配；
- 不存在交付清单声称存在但实际缺失的文件。

### 9.3 视觉验收

- 使用正式 PDF 或可信 DOCX 渲染器逐页渲染；
- 检查中文乱码、文字重叠、表格裁切、孤行、空白页和异常分页；
- 老板版保持 5–8 页；
- 专业附录允许随资料和税种数量增长；
- 渲染器不可用时记录未完成，不宣称通过。

## 10. 非目标

本阶段不建设仪表盘、不提供总体健康分、不自动发布外部商店、不改变税务规则公式、不要求税务专业人员审批、不让生成模型自主撰写最终税务结论，也不承诺在缺少申报和证据资料时给出完整税务判断。
