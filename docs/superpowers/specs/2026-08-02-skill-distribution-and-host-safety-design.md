# OpenTaxCheck 多商店 Skill 发行与宿主安全设计

**日期：** 2026-08-02

**状态：** 已确认设计，待实施

**范围：** Skill 行为约束、模型建议、多商店发行包、宿主安装与回归验证

## 1. 背景与目标

OpenTaxCheck self-service v1 已具备统一 Python/CLI/JSON 核心、可恢复案件、客户补件、中文报告和七宿主离线回放。Hermes 与 WorkBuddy 的真实测试进一步暴露了宿主层风险：智能体可能把账簿推断标成客户确认、用已缴税额反推计税依据、把初筛描述为检查完成、将未复核候选写进客户结论，或者声称交付了实际不存在的文件。

本项目同时需要面向多元 Skill 商店。GitHub 不能成为唯一入口；WorkBuddy、Qoder、腾讯 SkillHub、扣子等渠道应共享同一业务版本，而 Hermes 可直接从 GitHub 安装。目标是让客户只需向当前 AI 智能体发出安装指令，即可通过该宿主的首选渠道安装、验证并使用同一版本的 OpenTaxCheck。

本设计实现以下结果：

- 以一份规范发行包为唯一业务来源，通过多个商店和宿主适配层分发；
- 将事实确认、客户结论和完成状态的边界固化为 Skill 与机器合同；
- 提供可更新的模型建议，但不让模型参与确定性税务计算；
- 安装后必须校验版本、文件、依赖、权限和虚构案例；
- 将 Hermes、WorkBuddy 实测失败转化为永久回归场景。

## 2. 设计原则

- Python 核心是计算、状态、血缘和审计的唯一权威；AI 智能体只负责对话、解释和整理候选事项。
- 商店是可替换分发渠道，不是业务逻辑或版本真相来源。
- 一份核心 Skill 对应一个发行版本；渠道包不得复制或修改税务规则。
- 客户确认必须有结构化确认记录、确认人、带时区时间戳和证据引用。
- 报告生成不依赖税务专业人员签字，但必须如实保留资料限制、未确认事项和免责声明。
- 模型推荐不构成硬依赖；没有推荐模型时，确定性引擎仍可在 `assist` 或 `off` 模式运行。
- GitHub 是 Hermes 的主安装源，也是其他渠道的备用源之一，但不是全局唯一入口。

## 3. 发行架构

### 3.1 规范发行包

项目维护一份宿主无关的 OpenTaxCheck Skill，包括：

- `SKILL.md` 与专业参考资料；
- Python 核心版本和依赖约束；
- 规则包及其覆盖期间；
- 客户开场、补资料、初版报告和最终交付话术合同；
- 事实确认与客户结论准入规则；
- 安装自检和虚构案例；
- 模型建议配置；
- 发行清单与文件 SHA-256。

渠道包只能增加平台要求的简介、图标、分类、权限说明、安装入口和启动包装。渠道包不得维护独立计算公式、规则副本或不同版本的客户话术。

### 3.2 渠道分层

| 渠道类型 | 首批平台 | 分发方式 |
| --- | --- | --- |
| 原生 Skill 商店 | WorkBuddy、Qoder、腾讯 SkillHub | 在当前智能体对话或商店中搜索并安装 OpenTaxCheck |
| 本地 Skill 宿主 | Codex、Claude Code、OpenClaw | 使用宿主支持的本地 Skill 目录或安装命令，商店不可用时使用可信备用源 |
| GitHub 安装 | Hermes | 从 `MasterBenC/open-tax-check` 获取宿主包，校验后安装 |
| 插件/工作流平台 | 扣子 Coze | 使用薄适配器调用统一 Python/CLI/JSON 合同，不复制税务逻辑 |

实际商店上架需要平台账号和人工发布动作。本轮实现可提交的渠道包、元数据、安装指令和本地验证，不自动操作外部平台账号。

### 3.3 仓库布局

```text
distribution/
  manifest.json
  universal/
  workbuddy/
  qoder/
  skillhub/
  coze/
  codex/
  claude-code/
  openclaw/
  hermes/
```

`universal/` 包含规范 Skill 的不可变发行副本；其他目录只包含渠道适配资产。Hermes 目录提供 GitHub 安装卡片和验收入口，不建设不存在的 Hermes 商店包。

## 4. 统一发行清单

新增版本化的 `opentaxcheck-distribution/v1` 清单，至少记录：

- Skill 名称和版本；
- Python 核心版本与支持的 Python 3.11–3.13；
- 规则包版本和正式覆盖期间；
- 规范 Skill 文件列表及 SHA-256；
- 模型建议配置版本；
- 各渠道适配包版本和对应核心版本；
- 必需与可选依赖；
- 文件、终端、本地写入和联网权限说明；
- 虚构案例标识及预期自检结果。

首版使用 SHA-256 和商店发布者身份完成完整性校验，不新增自建签名服务。未来启用独立下载站或自动更新服务时，再扩展数字签名字段；扩展必须保持 v1 读取兼容。

## 5. 安装体验

### 5.1 商店宿主

面向 WorkBuddy、Qoder 和腾讯 SkillHub 的建议用户指令为：

> 请在你的 Skill 商店搜索并安装 OpenTaxCheck。安装完成后运行自检，并告诉我 Skill 版本、规则包版本、Python 环境和自检结果。

智能体优先使用当前平台商店。商店不存在、未上架或版本落后时，才提示可信备用渠道；不得静默安装来源不明的副本。

### 5.2 Hermes

Hermes 的建议用户指令为：

> 请从 MasterBenC/open-tax-check 安装 OpenTaxCheck Skill，核对发行版本和文件哈希，安装 Python 依赖，然后运行虚构案例自检。自检未通过时不要处理客户资料。

Hermes 必须读取仓库中的专用安装卡片，安装同一规范 Skill，并返回与商店宿主相同的自检字段。

### 5.3 安装自检

所有渠道按相同顺序执行：

1. 读取并验证 `opentaxcheck-distribution/v1`；
2. 校验核心 Skill 版本、规则包版本和文件 SHA-256；
3. 校验 Python 3.11–3.13；
4. 安装或验证所选功能需要的依赖；
5. 检查文件读取、终端执行和本地写入权限；
6. 运行不含客户资料的最小虚构案例；
7. 输出中文安装结果。

成功回复必须包含 Skill 版本、规则包版本、Python 版本、权限状态和虚构案例结果。失败必须明确区分商店未找到、版本过旧、Python 不兼容、权限不足、依赖失败、哈希不匹配和自检失败。任何失败均不得改写为安装成功；哈希或自检失败时不得处理客户资料。

## 6. 模型建议

新增独立的 `model-recommendations/v1` 配置。正式推荐模型为：

- DeepSeek V4；
- 腾讯混元 3（HY3）；
- GLM-5.2；
- GPT-5.6；
- Claude 4.8 及以上；
- Qwen 3.7 Max；
- Doubao Seed 2.0 Pro。

上述模型属于同一推荐档，不强制排序。Qwen 采用正式的 3.7 Max，不默认推荐预览版本；`qwen3.7-plus` 可作为成本平衡选项。豆包采用面向复杂推理与 Agent 的 Seed 2.0 Pro。配置不绑定带日期的供应商快照 ID，由宿主解析当前可用的对应正式版本。

不在名单中的模型仍可通过能力检查使用。宿主需要验证其结构化 JSON、中文长文、文件与终端工具调用、事实状态区分和案件状态保持能力；能力不足时从 `deep` 降级到 `assist` 或 `off`。模型名称和建议只出现在安装说明及环境检查中，不进入客户报告。

模型不得参与确定性税款计算，不得创建客户确认，不得改变 Python 返回的案件阶段，也不得覆盖未解决的资料缺口。

## 7. 事实确认防火墙

所有宿主使用四级事实状态：

| 状态 | 含义 | 可否进入正式测算 |
| --- | --- | --- |
| `observed` | 从账簿或材料直接观察到的值或文字 | 否，仅用于勾稽和追问 |
| `inferred` | AI 或程序推断的可能含义 | 否 |
| `customer_confirmed` | 客户明确回答并形成确认审计记录 | 是，但仍披露证据等级 |
| `evidence_verified` | 已与申报表、合同、发票等校验证据绑定 | 是 |

事实不得由宿主自行晋级。`customer_confirmed` 必须通过案件确认接口生成，至少包含问题 ID、确认人、带时区时间戳和有效证据引用；缺少确认审计事件时，任何内容都不得声称为客户确认。

根据已缴税额、账载税费或其他结果反推的税基一律保持 `inferred`，只能作为账务勾稽参考，不得作为正式计税依据。典型禁止项包括应交所得税除以税率反推应纳税所得额，以及用房产税、土地使用税账载金额反推计税依据。

## 8. 客户结论与智能体回复合同

OpenTaxCheck 核心统一生成客户摘要和智能体交付回复。宿主可以转述和轻微口语化，但不得改变事实等级、案件阶段、金额性质、资料缺口数量或结论强度。

规则如下：

- 有未解决资料或确认事项时，只能称“第一轮账务初筛完成”或“初版报告已生成”；
- `completed` 必须来自 Python 案件状态，宿主不得自行宣布；
- 试算合计必须标注“不代表应补税额、欠税金额或最终申报金额”；
- 没有申报表、缴款记录等反向证据时，不得使用“漏缴”“少缴”“违规”等定性词；
- `candidate` 或 `unreviewed` finding 不得进入客户风险结论，只能在允许的情况下作为待核实资料事项，或者保留在内部工作底稿；
- 客户交付清单只能列出当前发行清单中实际存在且哈希匹配的文件；
- 资料缺失、未执行程序、当地政策缺口和推断假设必须进入 limitations，不得留空；
- 宿主不得把 `needs_evidence` 改写为不适用或无风险。

统一初筛交付话术至少表达：已读取资料范围、待核对试算数量、重点核实事项数量、资料缺口数量，以及当前结果不代表最终应纳税额或应补税额。

## 9. 错误处理与恢复

- 商店不可用时显示具体渠道状态和可信备用渠道，不静默改变来源；
- 宿主包版本与核心版本不一致时阻止运行并提示升级；
- 文件哈希不匹配时停止安装或升级，保留原有可用版本；
- Python 或依赖安装失败时保留诊断信息，但客户侧只展示可执行的中文恢复建议；
- 自检失败时禁止读取客户资料；
- 案件执行失败时继续遵守现有不可变运行记录和可恢复状态，不复用旧成功结果；
- 模型不可用时降级 AI 模式，不影响确定性引擎和已有案件审计轨迹。

## 10. 验收与回归测试

### 10.1 Skill 行为回归

- 只有序时账时，不得把反推金额标为客户确认；
- 没有确认审计事件时，不得声称存在已确认事实；
- 存在待补资料时，不得说“税务健康检查已完成”；
- 未复核语义候选不得进入客户风险结论；
- 试算合计不得描述为应补税额；
- 输出文件不存在时，交付清单不得声称已经交付；
- Hermes 不得把待补资料税种自动关闭为“不适用”；
- WorkBuddy 不得把推断事实升级为确认事实。

这些场景以脱敏的 Hermes 和 WorkBuddy 回放夹具实现，测试的是结构化输出与禁止性短语，不依赖具体商业模型的隐藏推理。

### 10.2 发行验证

- 所有渠道包解析到相同核心版本；
- 各渠道解包后的规范 Skill 文件哈希一致；
- 渠道包不包含税务公式或规则副本；
- 清单中的每个交付文件实际存在且哈希匹配；
- 安装自检覆盖成功、商店不可用、依赖失败、权限不足、哈希失败和虚构案例失败；
- 模型建议配置通过 schema、正式版本名称和降级路径检查。

### 10.3 宿主验证

Codex 继续执行真实项目级 Skill 端到端验证；七宿主离线回放共享统一合同。WorkBuddy、Qoder、腾讯 SkillHub、扣子和其他外部宿主只有在实际平台运行并保存证据后，才能标记为 `runtime_verified`。商店包生成成功不等于商店上架或真实运行成功。

## 11. 非目标

本阶段不建设独立 Skill 商店、下载网站、自动商店发布服务或外部平台账号系统；不新增税务计算公式；不让 AI 替代客户确认；不要求税务专业人员签字；不承诺任意模型或宿主始终在线；不把商店审核通过等同于税务逻辑验证通过。

## 12. 实施顺序

1. 将 Hermes、WorkBuddy 实测问题转为失败回放和契约测试；
2. 实现事实状态与客户交付回复的硬性校验；
3. 增加模型建议 schema 和能力降级说明；
4. 增加统一发行清单和规范 Skill 归档；
5. 生成各宿主和商店渠道包；
6. 实现安装自检、完整性验证和中文结果；
7. 运行全量测试、构建和隔离安装验证；
8. 形成可人工提交到各商店的发行产物和上架清单。
