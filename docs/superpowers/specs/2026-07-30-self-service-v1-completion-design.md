# OpenTaxCheck 自助式公开 v1 收尾设计

日期：2026-07-30  
状态：依据发起人既有确认继续执行  
目标版本：v1.0.0

## 1. 目标

OpenTaxCheck v1 面向在客户宿主 Agent 中运行的中国企业税务健康自查。客户直接提供资料；宿主 AI 负责资料理解、字段建议、缺口追问和中文解释；Python 核心负责严格合同、来源绑定、金额与期间校验、勾稽、规则计算、状态和交付物。系统不要求税务专业人员批准后才能生成《税务健康检查报告》，但必须明确披露资料范围、未确认事实、未覆盖路径和免责声明。

v1 的完成定义是：新用户能够安装项目，用一条命令运行完整虚构案件，并通过 Codex、Hermes、WorkBuddy、扣子、Qoder、Claude Code 或 OpenClaw 中任一宿主完成“资料接收 -> 补件 -> 确定性检查 -> 中文报告/工作底稿/证据包”闭环；GitHub 提供可验证的 v1.0.0 标签和 Release。

## 2. 首发边界

### 2.1 包含

- 中国境内单一居民企业，检查期间为 2023-01-01 至 2026-12-31。
- 商贸、一般服务、软件科技、建筑设计和一般制造业的基线自查。
- 全国 18 个税种及教育费附加、地方教育附加，共 20 个项目的适用性筛查。
- 仓库已审计的正式计算路径；所有计算只使用客户确认、带证据引用且通过合同校验的事实。
- `.xlsx`、`.xlsm`、`.xls`、CSV、可复制文字 PDF、扫描 PDF、PNG、JPEG 和安全压缩包输入。
- 序时账、试算平衡表、资产负债表、利润表、现金流量表和纳税申报表的标准化数据合同。
- 本地 OCR、宿主抽取和经逐文件或逐页授权的云抽取合同。
- 客户自助式中文报告、专业结构的 Excel 工作底稿、DOCX、PDF 和可验证证据包。
- 七类宿主 Agent 的共同安装、运行、补件和交付合同。

### 2.2 不包含

- 自动申报、自动调账、自动向税务机关或第三方发送资料。
- 对房地产、金融、保险、证券、烟草、石油等特殊行业宣称完整覆盖。
- 自动选择地方政策、税目、优惠、核定征收、非居民、复合计税、预征清算、贸易救济税或其他未建模路径。
- 保证任意版式文档可无人工确认地正确解析。
- 独立网页或桌面 UI。

上述非目标不得静默忽略。报告和机器结果必须逐项列出未覆盖路径和后续需要客户确认的资料。

## 3. 决策

采用“宿主 AI + 严格 Python 合同”的混合架构。

不采用 Python 尝试理解所有任意格式：模板数量、地方差异和版式变化会导致不可审计的错误。不采用完全由 AI 输出结论：金额、期间、税率和证据无法稳定复现。常见表格由 Python 直接读取；复杂 PDF、图片或非标准表格由宿主 AI 转为严格合同；Python 对合同进行结构、来源、期间、金额、勾稽和规则约束。

## 4. 数据合同

### 4.1 `financial-statement/v1`

顶层字段固定为：

- `schema_version`：必须为 `financial-statement/v1`；
- `statement_id`、`source_id`、`entity_name`；
- `statement_type`：`balance_sheet`、`income_statement` 或 `cash_flow_statement`；
- `period_start`、`period_end`、`as_of_date`；
- `currency`、`unit_multiplier`；
- `lines`、`totals`、`issues`。

每个行项目包含稳定行代码、原始名称、标准名称、本期金额、上期金额、来源页码/工作表/单元格或坐标、置信来源和确认状态。金额使用十进制字符串，不接受浮点数、指数记法、`NaN`、`Infinity` 或超过预算的数值。宿主 AI 结果默认是 `proposed`；只有客户确认或确定性模板映射且勾稽通过后才成为 `confirmed`。

### 4.2 `tax-return/v1`

顶层字段固定为：

- `schema_version`：必须为 `tax-return/v1`；
- `return_id`、`source_id`、`entity_name`；
- `tax_id`、`return_type`、`period_start`、`period_end`；
- `filing_status`、`filed_at`、`currency`、`unit_multiplier`；
- `lines`、`totals`、`issues`。

每个申报行包含表单代码、行号、原始名称、标准事实键、金额或选项值、来源定位、置信来源和确认状态。申报表出现不支持的版本、重复关键行、期间冲突或来源不完整时不得生成确认事实。

### 4.3 来源和确认

两类合同都必须绑定案件清单中的 `source_id` 和文件哈希。导入时不信任宿主提供的文件名、媒体类型、实体、期间或来源定位；Python 从案件清单重新绑定并验证。任何进入税务计算的事实必须是 `confirmed`，带至少一个已验证证据引用和确认时间。AI 不得把 `observed` 或 `inferred` 升级为 `confirmed`。

## 5. 处理架构

```text
案件输入
  -> 安全清单、解包、哈希和类型识别
  -> Excel/CSV 直接读取 或 PDF/图片抽取
  -> 财务报表/申报表严格合同
  -> 标准化与交叉勾稽
  -> 缺口和冲突问题队列
  -> 客户确认回写
  -> 20 项税费筛查与正式计算
  -> 交付一致性检查
  -> workpaper.xlsx + report.docx/pdf + evidence bundle
```

模块边界：

1. `structured_documents.py`：两类合同、严格解析和序列化。
2. `structured_document_providers.py`：模板、宿主和云端导入边界。
3. `financial_reconciliation.py`：报表内部、账套至报表、账套/报表至申报表勾稽。
4. `case_orchestration.py`：可恢复的全案件状态机和补件任务。
5. `workpaper.py`：从同一案件快照生成 Excel 工作底稿。
6. 现有 `tax_health.py`、`tax_reporting.py` 和 `evidence_bundle.py` 继续负责确定性检查及报告/证据交付，不复制业务状态。

## 6. 状态和交互

自助式 v1 使用以下对外状态：

- `waiting_for_materials`：关键资料缺失；
- `waiting_for_extraction`：文档尚未完成抽取；
- `waiting_for_customer_confirmation`：映射、事实、税目、地方参数或冲突等待客户确认；
- `blocked_data_quality`：借贷不平、报表不平或关键勾稽失败；
- `ready_for_self_check`：输入足以运行当前已覆盖程序；
- `completed_with_limitations`：报告已生成，同时存在明确的资料或规则覆盖限制；
- `completed`：已覆盖程序均执行，且没有未披露阻塞项；
- `failed`：安全、合同或运行错误。

每个状态必须提供稳定 `next_action`、中文客户问题、所需证据类型和受影响税种。宿主 AI 只能展示或收集这些任务，不得自行改变状态或计算结果。

## 7. 勾稽规则

必须实现并保留逐项证据：

- 序时账借贷平衡；
- 试算平衡表期初、发生额和期末平衡；
- 序时账汇总至试算平衡表；
- 资产负债表资产等于负债加所有者权益；
- 利润表关键小计与净利润关系；
- 现金流量表期初、净增加额和期末现金关系；
- 试算平衡表至三张财务报表的可映射项目差异；
- 增值税、企业所得税、个人所得税及附加等申报金额与账面/报表/税款记录的期间差异；
- 重复申报、缺失期间和跨期错配。

任何强制勾稽失败都进入 `blocked_data_quality`。借贷不平或强制勾稽失败不得进入正常结论；报告只能说明阻塞事实和所需修复资料。

## 8. AI 与外部服务

### 8.1 七宿主共同合同

Codex、Hermes、WorkBuddy、扣子、Qoder、Claude Code 和 OpenClaw 使用同一四类消息：案件状态、补件任务、结构化确认和交付结果。各生态只提供薄包装，不复制税务规则。

### 8.2 独立 CLI 模式

`off` 永不调用模型。`assist` 和 `deep` 仅在显式配置兼容的 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL` 后启用；密钥不写盘、不进日志、不进证据包。模型返回必须通过与宿主相同的严格合同。

### 8.3 外部企业信息与云 OCR

外部企业信息采用 provider 接口。风鸟使用客户自己的 `FN_API_KEY`；云 OCR 使用逐文件或逐页授权记录。外部服务不可用时只降低资料覆盖，不阻止本地确定性流程。网络返回永远是外部观察，不自动成为客户确认事实。

## 9. 四件套交付物

### 9.1 `税务健康检查工作底稿.xlsx`

固定工作表包括：项目概览、资料清单、抽取与映射、数据质量、账务勾稽、财报勾稽、申报勾稽、税费筛查、正式计算、客户问题、证据索引、规则版本、报告选取和运行记录。单元格包含来源超链接或稳定来源标识；不嵌入原始客户文件。

### 9.2 `税务健康检查报告.docx` / `.pdf`

报告包含封面、保密与免责声明、目的和范围、资料覆盖、执行摘要、重大事项、一般提示、计算结果、未覆盖路径、整改路线图、待确认事项、方法论和法规来源。所有面向客户的标题、状态和说明使用中文。DOCX、PDF 和机器快照来自同一不可变交付快照。

### 9.3 `税务健康检查证据包.zip`

沿用已实现的验证、确定性 ZIP、默认不复制原件和显式授权边界；加入财报/申报合同、勾稽结果、工作底稿摘要、宿主确认摘要和规则版本。不得包含原始请求、隐藏推理、密钥、联系方式、支付标识或未经授权的客户原件。

## 10. 安全和资源预算

- 压缩包拒绝绝对路径、`..`、符号链接、Windows reparse point、重复成员、大小膨胀和过深目录。
- 所有 JSON、文档页数、表格、行、单元格、字符串和金额都有独立及总量预算。
- 文件在读取前后校验身份；交付物使用同目录临时文件、`flush`、`fsync` 和原子替换。
- 日志和稳定错误码不回显客户值、路径、密钥或模型响应正文。
- 默认本地处理；任何联网传输必须有服务、范围、授权主体、时间、保留和撤回记录。

## 11. 完整虚构案件

仓库提供一个完全虚构的 2023–2026 单一居民企业案件，包含：

- 平衡的序时账和试算平衡表；
- 三张财务报表；
- 增值税、附加税费、企业所得税和个人所得税申报表；
- 一份扫描证明材料和一份数字 PDF；
- 至少一个需要客户补件后才能解除的冲突；
- 至少一个因未覆盖特殊路径而保留的限制。

一条命令必须从原始虚构资料生成四件套，并验证 ZIP、工作簿结构、DOCX/PDF 页面、隐私和可重复运行。示例不得依赖真实客户、联网服务或未缓存模型。

## 12. 测试与发布门禁

发布前必须全部满足：

1. Windows、macOS、Linux 的 Python 3.11、3.12、3.13 测试矩阵通过。
2. 核心、Excel、OCR、财报/申报、勾稽、规则、报告、工作底稿和证据包测试通过。
3. `off` 完整案件通过；`assist`/`deep` 使用记录回放或虚构兼容服务验证严格合同。
4. 七宿主的安装发现、任务字段和交付字段契约测试通过。
5. wheel 和 sdist 内容严格、大小受限；安装后的 wheel 在隔离环境运行完整虚构案例。
6. 敏感信息、真实客户名称、密钥、第三方商标和受保护模板扫描通过。
7. DOCX、PDF 和 XLSX 完成结构与逐页/逐表视觉检查。
8. GitHub Actions 全部通过，远端 `main`、`v1.0.0` 标签和 Release 指向同一提交。
9. README 从“未发布 v0.1”更新为准确的 v1 安装、运行、限制和维护说明。

任何跳过的动态测试必须标明原因；跳过不等于通过。云端 provider 没有凭证时使用严格的合同/回放测试，不能宣称真实云调用通过。

## 13. 交付顺序

为保持每个边界可测试，按以下顺序实施：

1. 财报/申报严格合同与来源绑定；
2. 常见 Excel 模板和宿主导入；
3. 财报、账套和申报表交叉勾稽；
4. 全案件状态机和客户补件任务；
5. Excel 工作底稿和统一交付快照；
6. 安全压缩包、云/企业信息 provider 和七宿主包装；
7. 完整虚构案件与安装回放；
8. 文档、CI、发行审查和 GitHub v1.0.0 发布。

每一步都必须以测试通过、独立审查和可恢复提交结束。不得为后续任务故意留下失败测试。
