# 高频账税交叉检查设计

**日期：** 2026-08-05

**状态：** 已确认，待实施计划

## 1. 目标

在不改变现有借贷平衡、结构化文档质量门槛和确定性税额计算边界的前提下，新增一个独立的账税交叉检查层。第一版固定检查账套、财务报表、增值税申报表和企业所得税年度申报表之间的五类高频差异，并把差异转成来源可追溯的风险事项和有上限的 AI 智能体补件任务。

本阶段解决三个问题：

1. 账套、财报和申报表目前主要各自校验，缺少统一的高频跨来源差异结果；
2. 数据质量错误与真实税务差异必须分开，不能把金额不一致一律当作导入失败；
3. AI 智能体可以追问和记录解释，但不能自行放宽阈值、猜测事实或关闭风险。

## 2. 范围

第一版只实现以下五项检查：

| 检查编号 | 检查内容 | 影响税种 |
| --- | --- | --- |
| `BOOK-FS-REV-001` | 账套主营业务收入、其他业务收入合计与利润表营业收入核对 | 企业所得税、增值税 |
| `FS-VAT-SALES-001` | 利润表营业收入与增值税申报销售额核对 | 增值税、企业所得税 |
| `BOOK-VAT-OUTPUT-001` | 账套销项税额与增值税申报销项税额核对 | 增值税 |
| `FS-CIT-REV-PROFIT-001` | 利润表营业收入、利润总额与企业所得税年度申报表核对 | 企业所得税 |
| `BOOK-CIT-BE-001` | 账套业务招待费与企业所得税纳税调整明细及法定扣除限额核对 | 企业所得税 |

本阶段不实现工资薪金、研发费用、关联交易、资产损失、视同销售自动判定或地方政策推断。这些项目只能作为后续独立设计进入规则库。

## 3. 架构边界

新增 `src/open_tax_check/tax_cross_checks.py`。该模块只负责：

- 消费已经确认来源绑定的标准化账套行；
- 消费已经通过结构解析的财务报表和纳税申报表；
- 使用受控科目分类汇总账套金额；
- 执行五项固定交叉检查；
- 计算差异金额、差异比例和阈值结果；
- 输出稳定机器合同和建议补件问题。

现有模块职责保持不变：

- `quality.py` 和 `reconciliation.py` 继续负责凭证借贷平衡、试算平衡表和账套质量；
- `structured_reconciliation.py` 继续负责主体、期间、币种、单位、财报恒等式和结构化文档内部勾稽；
- `tax_calculation.py` 和税额规则包继续负责有事实、有证据的确定性税额计算；
- 报告层只渲染交叉检查结果，不重新计算金额；
- 宿主 AI 智能体只展示问题和提交结构化确认。

数据流固定为：

```text
标准化账套 + 财务报表 + 纳税申报表
                  |
          基础上下文与质量门槛
                  |
           五项账税交叉检查
                  |
    差异结果 + 来源 + 影响税种 + 补件问题
                  |
       风险报告 / AI 追问 / 确认后增量重跑
```

## 4. 输入合同

交叉检查输入必须包含：

- 标准化序时账及其来源清单哈希；
- 已确认映射、科目分类和检查期间；
- 财务报表结构化合同；
- 纳税申报表结构化合同；
- 主体名称、期间、币种和单位倍数；
- 可验证的来源 ID、表单代码、行号或账套科目标识。

账套金额只能由明确受控的科目分类汇总。不得用模糊关键词从任意摘要、客户对话或 OCR 原文推定主营业务收入、其他业务收入、销项税额或业务招待费。未分类、分类冲突或来源映射未确认时，对应检查返回 `not_performed`。

借贷不平衡、试算平衡表勾稽失败或结构化文档上下文不一致时，不得执行金额比较。

## 5. 输出合同

整批运行返回一个不可变容器，包含：

- `schema_version`：第一版固定为 `tax-cross-checks/v1`；
- `status`：只允许 `completed` 或 `blocked_data_quality`；
- `results`：按五项固定检查顺序排列的结果；
- `questions`：去重并排序后的待补件问题；
- `source_manifest_sha256`：本次输入来源清单哈希；
- `audit_events`：追加式状态和客户确认事件引用。

当批次状态为 `blocked_data_quality` 时，`results` 和 `questions` 均为空，阻断原因继续引用现有账套或结构化文档质量结果，不在交叉检查层复制另一套质量诊断。

每项检查输出一个不可变结果，至少包含：

- `check_id`：固定检查编号；
- `tax_ids`：受影响税种；
- `status`：`matched`、`within_tolerance`、`difference_found` 或 `not_performed`；
- `ledger_amount`：账套侧金额，不适用时为空；
- `comparison_amount`：对比侧金额，不适用时为空；
- `difference_amount`：两侧金额的绝对差；
- `difference_ratio`：相对于两侧绝对金额较大值的比例；两侧均为零时为 `0`；
- `absolute_tolerance`：固定为 `10.00`；
- `relative_tolerance`：固定为 `0.0001`；
- `period_start` 和 `period_end`；
- `source_refs`：两侧来源 ID、科目分类、表单代码和行号；
- `title_zh`：客户可读中文标题；
- `reason_codes`：允许追问的合理差异类别；
- `question`：可选的结构化补件问题；
- `audit_refs`：客户解释和状态变化引用。

金额统一使用 `Decimal` 和现有精确运算工具。机器 JSON 中金额继续使用规范字符串，不使用二进制浮点数。

## 6. 差异与阈值

差异金额定义为：

```text
abs(ledger_amount - comparison_amount)
```

差异比例定义为：

```text
difference_amount / max(abs(ledger_amount), abs(comparison_amount))
```

当两侧金额均为零时，差异比例为 `0`，不得除零。当一侧为零、另一侧非零时，差异比例为 `1`。

状态判断顺序固定为：

1. 必要来源、金额或受控分类缺失：`not_performed`；
2. 两侧金额完全一致：`matched`；
3. 差异金额不超过 `10.00`，并且差异比例不超过 `0.0001`：`within_tolerance`；
4. 其他情况：`difference_found`。

两个容差条件必须同时满足。AI、命令行参数或客户回答不得覆盖阈值。未来调整阈值必须升级检查规则版本并保留旧结果的版本信息。

## 7. 数据质量与风险分离

以下情况属于数据质量阻断：

- 主体不一致；
- 检查期间不一致；
- 币种不一致；
- 单位倍数不一致；
- 账套借贷不平衡；
- 试算平衡表勾稽失败；
- 结构化来源合同本身存在阻断问题。

阻断时交叉检查整体状态为 `blocked_data_quality`，不生成虚假金额差异。

资料有效但两侧金额不同属于税务风险线索，不阻断报告生成。`difference_found` 进入客户风险事项；`within_tolerance` 保留在机器快照和审计附录中，但不进入客户重点风险清单。

## 8. 五项检查细则

### 8.1 `BOOK-FS-REV-001`

账套侧汇总已确认分类为主营业务收入和其他业务收入的发生额，报表侧读取利润表营业收入。缺少任一受控分类或报表行时返回 `not_performed`。

### 8.2 `FS-VAT-SALES-001`

财报侧读取利润表营业收入，申报侧汇总检查期间内增值税申报销售额。月度或季度申报必须完整覆盖检查期间，重叠或缺期返回 `not_performed`。差异只代表需要解释，不代表漏报收入。

### 8.3 `BOOK-VAT-OUTPUT-001`

账套侧汇总已确认分类为销项税额的发生额，申报侧汇总增值税申报销项税额。进项转出、简易计税、代扣代缴或其他非销项项目不得混入。

### 8.4 `FS-CIT-REV-PROFIT-001`

分别核对利润表营业收入与企业所得税年度申报收入、利润表利润总额与年度申报利润总额。两个子项独立记录金额和差异，但共享一个检查编号和一个去重后的客户问题。

### 8.5 `BOOK-CIT-BE-001`

账套侧读取业务招待费受控分类，申报侧读取纳税调整明细中的账载金额和税收金额。法定扣除限额继续调用现有 `business_entertainment_adjustment`，不得复制公式。检查结果同时展示账套金额、申报账载金额、申报税收金额、程序计算扣除额和应调增额；任一必要事实缺失时返回 `not_performed`。

## 9. AI 智能体追问

只有 `difference_found` 和 `not_performed` 生成问题。问题按以下顺序排序：

1. 数据缺失导致关键检查无法执行；
2. 绝对差异金额较大的项目；
3. 相同金额下相对差异较大的项目；
4. 固定检查编号顺序。

一次宿主交互最多展示 3 个问题。相同检查、相同期间和相同来源组合只生成一条问题。

第一版允许的解释类别固定为：

- `unbilled_revenue`：未开票收入；
- `deemed_sale`：视同销售；
- `non_taxable_or_exempt_revenue`：不征税或免税收入；
- `tax_inclusive_conversion`：价税分离；
- `timing_difference`：跨期差异；
- `amended_return`：申报更正；
- `book_adjustment`：账务调整；
- `other`：其他，必须提供文字说明和证据。

AI 智能体不得自行选择解释类别、生成客户确认、判断解释真实或把差异改写为已解决。

## 10. 客户确认与增量重跑

客户解释必须包含：

- 对应 `check_id`；
- 解释类别；
- 非空中文说明；
- 客户确认人和确认时间；
- 至少一个能通过现有来源验证的证据引用。

确认只触发受影响检查重跑。风险只有在解释合同有效、证据引用可验证且重跑结果已经持久化后，才能转为 `explained_pending_verification` 或 `closed`。`closed` 还必须有确定性金额桥接，证明两侧差异已被已确认项目完整解释；仅有文字说明不得关闭风险。

审计记录永久保留原金额、原状态、客户解释、证据、重跑结果和状态变化。宿主不能覆盖旧事件。

## 11. 报告呈现

客户 PDF 使用中文展示：

- 发现了什么；
- 两侧金额和差异；
- 为什么需要关注；
- 当前不能下什么结论；
- 需要补什么资料；
- 建议下一步。

报告不显示内部枚举、Python 字段名、检查实现细节或未经客户确认的合理差异原因。`matched` 不宣称税种无风险；`within_tolerance` 不进入重点风险，但在专业附录保留检查事实；`not_performed` 明确写为资料不足，不能写成金额一致。

## 12. 错误处理与安全

- 所有来源沿用现有路径、哈希、symlink 和 Windows reparse point 防护；
- 汇总只读取已经冻结的内存快照，输入在清单生成后变化时失败关闭；
- 日志不得输出客户完整路径、原始单元格内容或无关个人信息；
- 重复申报期间、重叠申报表、缺失申报期间和单位换算冲突均不得静默合并；
- 任一子检查异常不得污染已持久化结果或活动交付指针；
- PDF 失败继续按 v3 交付合同失败关闭，不回退 Word。

## 13. 测试策略

严格采用测试驱动开发，至少覆盖：

1. 五项检查分别完全一致、容差内、绝对阈值超限和比例阈值超限；
2. 两侧为零、一侧为零、负数和大额精度；
3. 主体、期间、币种和单位不一致时阻断；
4. 缺少账套、财报、申报表或必要行时 `not_performed`；
5. 借贷不平衡和试算平衡表失败时不执行；
6. 来源 ID、科目分类、表单代码和行号完整可追溯；
7. 输入变化后旧结果失效；
8. 问题去重、确定性排序和最多 3 个；
9. 无证据、无说明或非法解释类别不能改变状态；
10. 客户确认只重跑受影响检查；
11. 只有完整金额桥接才能关闭风险；
12. PDF 显示中文金额、差异、证据边界和下一步，不泄露内部状态码；
13. CSV 与 Excel 对相同虚构业务产生一致结果；
14. 完整回归、构建、严格发行校验和隔离 wheel 安装通过；
15. Windows、macOS、Linux 与 Python 3.11–3.13 的 CI 通过。

## 14. 验收案例

使用完全虚构且来源绑定的五类案例：

1. 五项全部一致；
2. 仅存在报表取整差异，全部落在双阈值内；
3. 增值税销售额和销项税额存在超阈值差异；
4. 企业所得税收入、利润和业务招待费存在超阈值差异；
5. 多项资料缺失，AI 智能体分批补件后只重跑受影响检查。

每个案例必须验证机器结果、补件任务、审计事件、报告视图和交付快照的一致性。

## 15. 完成标准

- 五项检查的公开机器合同、持久化和增量重跑实现完成；
- 数据质量阻断与税务风险差异保持独立；
- 双阈值按本设计精确执行，且不可由 AI 或客户覆盖；
- 问题队列有上限、去重并来源可追溯；
- PDF 客户报告正确呈现五项检查结果及证据边界；
- 全部新增测试先红后绿；
- 完整测试、构建、严格发行校验、隔离 wheel 安装和跨平台 CI 通过；
- 独立复审无 Critical 或 Important 问题；
- 不改变借贷必须平衡、客户确认必须有证据和正式报告只提供 PDF 的既有不变量。
