# OpenTaxCheck HTML/PDF 客户报告设计

**日期：** 2026-08-04  
**状态：** 已确认设计，待实施  
**范围：** 《税务健康检查报告》的信息架构、固定 HTML 排版、PDF 唯一正式交付和验收标准

## 1. 背景与目标

现有客户报告虽然能够汇总检查结果，但内容层级仍接近系统状态和检查反馈的集合；DOCX 在不同 Office、WPS 和操作系统间还会产生字体、目录、分页和表格漂移。新报告以用户提供的《风险检测_税务风险报告-第三版就很合适》为视觉和阅读体验参考，保留其正式咨询报告感、风险概览和统一事项结构，同时修正目录薄弱、长段落、资料缺失与风险等级混用、结论边界不清等问题。

正式客户交付只提供 PDF。HTML 是固定排版母版和 PDF 渲染输入，不作为需要客户编辑的报告格式；不再生成或交付 Word/DOCX 报告。

## 2. 产品原则

- 报告先回答管理层“发现了什么、影响什么、先做什么”，再提供专业证据和计算细节。
- 所有客户结论均来自确定性报告视图模型；宿主 AI 可以解释，不得新增、升级或改写税务结论。
- 不提供总体健康分、无依据的风险概率或精确百分比。
- 资料状态与风险等级分开表达，资料缺失本身不得包装成高、中、低税务风险。
- “本次检查未触发异常”只描述已执行程序，不得简写为“无风险”。
- 试算金额不得表述为应补税额、欠税金额或最终申报金额。
- 页面必须保持统一中文字体、稳定分页和可复现的 A4 版式。
- PDF 生成失败时交付失败，不得用 DOCX、Markdown 或未经验证的文件冒充正式报告。

## 3. 输出架构

报告流水线固定为：

```text
案件快照 + 已复核 findings + 资料覆盖状态 + 规则来源
                    ↓
        tax-health-report/v3 视图模型
                    ↓
          固定 HTML 模板与打印 CSS
                    ↓
        受控 Chromium A4 PDF 渲染
                    ↓
          逐页结构与视觉质量校验
                    ↓
             正式客户 PDF
```

视图模型负责事实、状态、顺序和文字强度；HTML 模板只负责呈现，不执行税务判断。渲染器不允许联网加载字体、样式、脚本或图片，所有必要资源必须随包提供或以内联形式使用。

## 4. 正式报告目录

### 4.1 封面

展示企业名称、检查期间、报告名称“税务健康检查报告”、报告日期、报告编号、修订号和保密标识。不得在封面显示内部状态码、规则 ID 或技术版本号。

### 4.2 阅读提示

用一页以内说明检查目的、资料基础、报告性质、金额边界和责任边界。免责声明采用可读短句，不堆叠法律式长段落。

### 4.3 税务健康检查结论

管理层摘要直接展示：

- 本次检查状态及一句话结论；
- 重点核实事项数量；
- 重要资料缺口数量；
- 有管理意义的试算事项及金额性质提示；
- 最优先处理的三项行动。

摘要不得出现内部英文状态码、原始 JSON 字段或未解释的算法指标。

### 4.4 风险全景

采用四类并列概览：重点核实、中等关注、一般提示、资料待补。颜色只用于快速区分，不生成环形健康分或暗示统计精度的百分比。每类显示事项数量和简短标题，可跳转至对应正文。

### 4.5 优先处理清单

按优先级列示事项、涉及税种、影响期间、金额性质、建议动作、建议时限和当前责任方。排序由确定性规则产生，同一输入必须得到相同顺序。

### 4.6 重点风险详解

每项采用一致结构：

1. 发现了什么；
2. 为什么值得关注；
3. 涉及税种和期间；
4. 数据、凭证和计算依据；
5. 适用规则及适用条件；
6. 当前能够得出的结论；
7. 当前不能得出的结论；
8. 建议处理动作；
9. 尚需补充或确认的资料。

正文优先使用短段落、表格和关键数值，避免复制通用自查教材。完整公式、证据链和规则版本放入附录。

### 4.7 分税种检查结果

按增值税、企业所得税、个人所得税、印花税、房产税、城镇土地使用税、契税及其他适用税费汇总。每个税种只显示适用状态、已执行程序、触发事项、资料限制和正文链接，不重复重点风险全文。

### 4.8 资料范围与检查边界

每份预期资料必须归入下列一种客户可读状态：

| 状态 | 报告用语 |
| --- | --- |
| 未提供 | 截至报告生成时未收到 |
| 已收到待处理 | 已收到，等待识别或结构化 |
| 提取不完整或失败 | 已收到，但部分内容暂未可靠提取 |
| 合同校验失败 | 已提取，但结构或来源校验未通过 |
| 已导入待确认 | 已进入案件，但关键值仍待客户确认 |
| 已导入并核对 | 已完成导入及本次范围内核对 |

已经上传至当前 AI 智能体的资料不得写成“未提供”。资料限制必须同时说明受影响的税种、程序或结论，不使用笼统的“建议 OCR 后重跑”。

### 4.9 附录

附录收纳：

- 全部已执行检查项，包括未触发异常的项目；
- 证据来源、数据期间和文件哈希；
- 计算公式、口径、税率和金额性质；
- 规则名称、版本、适用期间和官方来源；
- 资料覆盖矩阵和未执行程序；
- 报告修订信息。

正常项目统一表述为“本次检查范围内未触发异常”，并列示实际执行程序和资料边界。

## 5. 视觉与排版系统

- 页面规格为 A4 纵向，固定页边距、页眉、页脚和页码。
- 使用随应用分发且允许嵌入的中文字体；正文、标题、数字和表格均定义明确字体栈，不依赖客户电脑字体。
- 正文以深灰和黑色为主，红、橙、蓝灰、绿色仅承担状态语义；不使用装饰性渐变和重复水印。
- 封面、目录、管理层摘要、风险全景和正文使用统一网格与间距体系。
- 表格跨页时重复表头，禁止截断单元格文字；标题不得孤立在页尾。
- 单项风险可以跨页，但标题、等级和核心结论必须作为不可拆分的起始块。
- 目录由实际章节生成，包含页码和 PDF 内部跳转链接。
- 页眉显示企业简称和报告期间，页脚显示保密标识、报告编号、修订号和页码。

## 6. 交付物与兼容性

客户正式交付物：

- `税务健康检查报告.pdf`

内部可审计材料继续保留机器快照、工作底稿、证据包和交付清单。渲染所用 HTML 可作为受控中间产物纳入证据包，但不列为客户正式报告。

报告协议升级为 `tax-health-report/v3`。v3 交付清单不得包含 `docx_report` 或把 Markdown 标为客户正式报告。旧 v2 案件保持可读取，但重新发布正式报告时必须按 v3 重新生成 PDF，不修改既有历史交付目录。

## 7. 失败处理

- 缺少 PDF 渲染能力：停止正式交付并返回明确错误。
- 字体资源缺失或字体未成功载入：停止渲染，不允许静默回退到不可控系统字体。
- HTML 模板、视图模型或资源版本不匹配：停止交付。
- 页面溢出、空白页、目录页码错误或链接失效：视觉验收失败，不发布 PDF。
- 某项资料仍在处理中：报告可以受限状态生成，但必须准确显示资料状态及受影响范围。
- PDF 已生成但哈希、页数或结构校验失败：删除临时交付，不更新当前交付指针。

## 8. 验收标准

### 8.1 内容验收

- 主报告只突出重点风险、重要提示和实质资料缺口，系统状态和全部正常项进入边界章节或附录。
- 每个重点事项均包含事实、影响、证据、规则、结论边界和行动建议。
- 已上传资料不会被错误标记为未提供。
- 资料缺失不被计算为税务风险等级。
- 所有金额标签和免责声明与机器快照一致。
- 相同案件修订和模板版本生成相同的章节、排序和客户文字。

### 8.2 自动化验收

- 视图模型、章节顺序、状态映射和事项排序具备单元测试。
- HTML 必须通过结构检查，包含唯一章节锚点、目录链接和必要元数据。
- PDF 必须为有效文件，页数大于零，包含可提取中文文本、目录书签、页码和报告编号。
- 交付清单仅声明实际存在且哈希匹配的产物。
- 发布包和隔离安装环境能够生成代表性 PDF。

### 8.3 视觉验收

至少覆盖普通案例、长文本压力案例、无重点风险案例和大量资料缺口案例。逐页渲染为图片后检查：

- 中文字体一致，无乱码、缺字或意外字体回退；
- 无文字重叠、内容裁切、表格破损、孤行标题和异常空白页；
- 目录页码与正文一致，内部链接可用；
- 风险颜色在彩色和灰度打印下均可区分；
- 主报告保持管理层可读，详细技术内容进入附录；
- Windows、macOS 和 Linux 的受控渲染结果满足相同结构规则。

PDF 视觉验收必须以实际 PDF 为依据，不能用 HTML 截图或结构测试替代。

## 9. 非目标

本阶段不建设在线报告门户，不允许客户编辑正式报告，不提供 Word/DOCX，不生成总体健康评分，不改变税务规则公式，不让生成模型自主决定税务结论，也不在本任务中扩展多商店发行。
